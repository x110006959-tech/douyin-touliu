# 全局工作台

* **生效日期：**2026-07-04
* **最近更新：**2026-07-18
* **适用范围：**本 Workspace 及以后在本 Workspace 内执行的所有项目

---

## 1. 工作台定位

全局工作台是本 Workspace 的最高管理入口，用于统一管理：

* Codex 的全局行为规则
* 新项目创建与归档规范
* 项目目录和文件归属
* Git 本地与远程版本状态
* 长期项目的状态、交接和安全边界
* 可复用经验、错误与踩坑记录

除非用户明确指定其他位置，否则项目相关文件必须保存在本 Workspace 内，不得散落到桌面、下载目录、临时目录或其他无关位置。

Workspace 根目录只保留代码仓库级文件和目录。临时资料、过程记录、零散交付物不得直接堆放在根目录。

## 2. 目录职责

本 Workspace 分为三个区域：

### 2.1 代码仓库区

用于保存实际运行的代码、数据库结构和工程配置：

```text
apps/
packages/
prisma/
package.json
pnpm-workspace.yaml
pnpm-lock.yaml
docker-compose.yml
```

代码仓库区可以位于 Workspace 根目录，不需要移动到 `10_项目档案`。

### 2.2 长期交接区

统一放在根目录的 `docs` 中，用于跨会话、跨阶段继续开发：

```text
docs/
  CODEX_HANDOFF.md
  CURRENT_TASK.md
  DECISION_LOG.md
  DEPLOYMENT_STATE.md
  PROJECT_STATE.md
  ROADMAP.md
  SAFETY_BOUNDARY.md
```

### 2.3 管理和项目档案区

```text
00_全局工作台/
10_项目档案/
```

* `00_全局工作台`：存放全局规则、全局 SOP 和全局踩坑记录。
* `10_项目档案`：存放每个项目的需求、过程、资料、交付说明和复盘内容。

## 3. Codex 全局工作规则

### 3.1 基本规则

1. 默认使用中文沟通和交付。
2. 开始项目任务前，先确认对应项目档案是否存在。
3. 如果项目档案不存在，先按照《新项目 SOP》创建。
4. 开工前必须检查并阅读当前目录中的 `AGENTS.md`。
5. 长期代码任务开始前，应阅读已有的项目交接文档。
6. 不覆盖用户已有文件；修改前必须先理解原内容，再进行增量编辑。
7. 不得擅自删除、回退或覆盖用户及其他流程产生的未提交改动。
8. 临时文件必须及时清理或归档，不得长期遗留在根目录。
9. 重要决策、结构调整和交付位置变化，应记录到项目总览或对应交接文档。
10. 遇到错误、返工、弯路或可复用方法时，应更新复利与踩坑记录。

### 3.2 代码工程规则

1. 前端、后端、插件和共享包必须保持职责分离。
2. 不得把大量无关功能集中写入同一个文件或同一个目录。
3. 应按照领域、模块或业务职责拆分代码。
4. 公共类型、常量和通用逻辑应优先放入共享模块。
5. 每个 API 至少需要提供：

   * 接口用途说明
   * 请求参数说明
   * 请求示例
   * 返回字段说明
   * 成功返回示例
   * 常见错误返回示例
6. 修改代码、架构、数据结构或安全边界后，应同步更新对应文档。
7. 不为了形式上的模块化进行无意义拆分；模块边界应清晰且可维护。

### 3.3 文件归属规则

* 全局规则、全局 SOP、全局日志只允许放在 `00_全局工作台`。
* 单个项目的需求、过程、交付和复盘放入对应项目档案。
* 实际运行代码继续保存在 `apps`、`packages`、`prisma` 等仓库目录。
* 跨阶段交接信息放入 `docs`。
* 仓库级说明文件可以保留在 Workspace 根目录。
* 不在根目录堆放截图、草稿、测试文件、导出文件或临时文档。

## 5. 项目执行流程

执行项目任务时，按以下顺序处理：

### 第一步：确认工作位置

确认当前所在目录属于本 Workspace，并检查：

* 项目档案是否存在
* `AGENTS.md` 是否存在
* 是否存在长期交接文档
* Git 工作区是否有未提交改动

### 第二步：读取现有规则和状态

优先读取：

1. `AGENTS.md`
2. `docs/CODEX_HANDOFF.md`
3. `docs/CURRENT_TASK.md`
4. `docs/PROJECT_STATE.md`
5. `docs/SAFETY_BOUNDARY.md`
6. 与当前任务直接相关的其他文档

不要求每次机械读取全部文档，但不得在不了解当前状态和安全边界的情况下直接修改长期项目。

### 第三步：执行任务

执行过程中：

* 优先增量修改
* 保持模块职责清晰
* 不破坏现有安全边界
* 不擅自处理无关改动
* 将过程资料存入正确目录
* 对关键变更进行必要验证

### 第四步：同步文档

根据实际变化更新：

| 发生的变化            | 需要更新的文档                    |
| ---------------- | -------------------------- |
| 当前任务或下一步变化       | `docs/CURRENT_TASK.md`     |
| 项目完成度或版本状态变化     | `docs/PROJECT_STATE.md`    |
| 产品或架构决策变化        | `docs/DECISION_LOG.md`     |
| 部署、端口、环境变量或数据库变化 | `docs/DEPLOYMENT_STATE.md` |
| 安全规则或禁止事项变化      | `docs/SAFETY_BOUNDARY.md`  |
| 项目目录、交付位置或重要决策变化 | `00_项目总览.md`               |
| 出现错误、返工或可复用经验    | 复利与踩坑日志                    |

### 第五步：验证和交付

任务完成后应说明：

* 修改了什么
* 影响了哪些文件或模块
* 执行了哪些验证
* 是否存在未完成项
* 是否进行了 Git 提交
* 是否已推送远程仓库

## 6. 命名规范

### 6.1 项目档案命名

所有项目统一放在 `10_项目档案`，格式为：

```text
project-三位编号-项目名称
```

示例：

```text
project-001-字节投流
project-002-小红书投放复盘
project-003-私域成交SOP
```

编号规则：

* 从 `001` 开始递增。
* 已使用的编号不得重复使用。
* 项目结束、暂停或删除后，原编号仍然保留。
* 项目名称应简短、明确、便于识别。

### 6.2 项目内部目录

每个项目优先使用以下固定结构：

```text
00_项目总览.md
01_需求与目标/
02_执行过程/
03_素材与资料/
04_交付物/
05_复盘与沉淀/
```

过程文档建议使用：

```text
YYYY-MM-DD_主题.md
```

示例：

```text
2026-07-04_首次需求梳理.md
2026-07-04_执行记录.md
2026-07-04_问题复盘.md
```

### 6.3 仓库级文档

Workspace 根目录允许保留：

* `README.md`
* `AGENTS.md`
* `MIGRATION_NOTES.md`
* `V版本号_ACCEPTANCE.md`

示例：

```text
V0.1_ACCEPTANCE.md
V0.1.1_ACCEPTANCE.md
V0.1.2_ACCEPTANCE.md
```

### 6.4 Git 提交命名

统一格式：

```text
类型: 简短说明
```

常用类型：

| 类型         | 用途           |
| ---------- | ------------ |
| `feat`     | 新增功能或版本能力    |
| `fix`      | 修复问题         |
| `docs`     | 更新文档         |
| `chore`    | 工程配置、依赖或目录调整 |
| `refactor` | 不改变外部行为的代码重构 |
| `test`     | 新增或调整测试      |

示例：

```text
feat: 完成 v0.1.1 数据复核与安全闭环
docs: 更新全局工作台规则
chore: 重构为 pnpm 工作区结构
```

## 7. 核心文档职责

### 7.1 全局文档

#### `00_全局工作台.md`

Workspace 的总入口，记录：

* 全局规则
* 目录职责
* 命名规范
* 项目执行要求
* Git 管理要求

仅在全局规则或管理方式发生变化时更新，不记录单个项目的业务细节。

#### `01_全局复利与踩坑日志.md`

用于记录具有复用价值的问题和经验。

每条记录至少包含：

* 日期
* 所属项目
* 问题
* 原因
* 修正动作
* 可复用方法

日志原则上只追加，不删除历史记录。

如果问题同时属于某个具体项目，也应在该项目的 `05_复盘与沉淀` 中保留记录。

#### `02_新项目SOP.md`

用于规定：

* 项目编号生成
* 项目目录创建
* 初始文档生成
* 资料归档
* 执行和交付流程

新项目流程变化时，优先更新该文件，并检查是否需要同步更新本工作台。

### 7.2 项目级规则

#### `AGENTS.md`

用于规定当前代码仓库的强约束，包括：

* 项目定位
* 技术栈
* 包结构
* 安全红线
* 开工前必读文档
* 验证要求
* 完成后的文档更新要求

如果 `AGENTS.md` 与全局规则存在差异，优先遵守更具体、且更接近当前项目的规则；之后再判断是否需要修正全局文档。

### 7.3 长期交接文档

| 文件                    | 主要职责                |
| --------------------- | ------------------- |
| `CODEX_HANDOFF.md`    | 当前项目的总交接入口          |
| `CURRENT_TASK.md`     | 当前任务、已完成内容和下一步      |
| `PROJECT_STATE.md`    | 项目总体完成度和版本状态        |
| `DECISION_LOG.md`     | 产品、架构和技术决策          |
| `DEPLOYMENT_STATE.md` | 部署环境、域名、端口、数据库和运行状态 |
| `ROADMAP.md`          | 中长期路线图              |
| `SAFETY_BOUNDARY.md`  | 安全边界、禁止事项和风险控制      |

文档已有未提交改动时，必须先阅读并保留原有有效内容，不得直接覆盖。

## 8. Git 版本管理

### 8.1 基本原则

* Git 提交用于保存本地版本快照。
* 本地提交不等于已经同步到 GitHub。
* 只有配置远程仓库并成功执行 `git push`，才算完成远程同步。
* 未经用户要求，不擅自提交、推送、回退或重写 Git 历史。

### 8.2 提交前检查

用户要求“提交一次 Git 版本”时，至少执行：

```bash
git status --short
git diff --stat
git diff
```

暂存后还应检查：

```bash
git diff --cached --stat
git diff --cached
```

## 9. 复利与踩坑记录触发条件

出现以下情况时，应更新日志：

* 同类错误重复出现
* 因目录混乱造成返工
* 因未读取文档导致覆盖或遗漏
* 因环境、依赖或版本问题导致启动失败
* 因安全检查不足导致敏感信息风险
* 因需求理解偏差导致返工
* 找到明显提高效率或质量的方法
* 形成可以复用的检查清单或标准动作

普通的小修改不需要机械记录，只有具有复用价值的经验才进入日志。
