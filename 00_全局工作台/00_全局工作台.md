# 全局工作台

生效日期：2026-07-04

最近更新：2026-07-08

适用范围：本 Workspace 以及以后在本 Workspace 内执行的所有项目。

## 1. 工作台目标

全局工作台是整个 Workspace 的最高入口，用来统一管理：

- Codex 的行为规则
- 新项目的创建规范
- 全局复利与踩坑沉淀
- 所有项目的目录结构和文件归属
- Git 版本管理与本地/远程状态说明
- 长期项目的交接文档、阶段状态和安全边界

除非用户明确指定其它位置，否则所有项目相关内容必须存放在本 Workspace 内，不能散落到桌面、下载目录、临时目录或电脑其它位置。

Workspace 根目录允许保留仓库级标准文件，例如 `README.md`、`AGENTS.md`、`package.json`、`pnpm-workspace.yaml`、`pnpm-lock.yaml`、`docker-compose.yml`、`prisma`、`apps`、`packages`、`docs` 等。禁止把临时资料、零散过程文件、未归档交付物直接堆在根目录。

## 2. Codex 行为规则

1. 默认使用中文沟通和交付。
2. 执行任何项目任务前，先确认对应项目文件夹是否存在。
3. 项目文件夹必须使用 `project-编号-项目名称` 格式，例如 `project-001-字节投流`。
4. 如果项目文件夹不存在，必须先按照《新项目SOP》创建，再开始执行项目内容。
5. 所有项目资料、过程文档、交付物、复盘内容，都必须放进对应项目文件夹。
6. 全局规则、全局日志、全局 SOP 只允许放在 `00_全局工作台`。
7. 不在 Workspace 根目录随意堆放零散文件。
8. 不覆盖用户已有文件；需要修改时，先理解原内容，再做增量更新。
9. 每次遇到错误、踩坑、返工、绕路、可复用方法时，应更新《全局复利与踩坑日志》。
10. 重要项目决策、目录调整、交付位置变更，需要在对应项目的 `00_项目总览.md` 中记录。
11. 如果存在 `AGENTS.md`，开工前必须读取并遵守其中的项目级规则。
12. 如果存在 `docs/CODEX_HANDOFF.md`、`docs/PROJECT_STATE.md`、`docs/SAFETY_BOUNDARY.md`、`docs/CURRENT_TASK.md`，长期任务开工前应先读取这些交接文档。
13. 代码、架构、数据结构、安全边界、部署状态、当前任务发生变化时，应同步更新 `docs` 下对应文档。
14. 用户要求“提交一次 Git 版本”时，必须先执行 `git status`、查看变更范围、检查敏感信息，再暂存和提交。
15. Git 提交默认只是提交到本地仓库；只有配置远程仓库并执行 `git push` 后，才算同步到 GitHub 或其它远程平台。
16. 如果发现已有未提交改动来自用户或其它流程，不得擅自回退；如需修改同一文件，必须先读懂现有内容后再增量编辑。

## 4. 命名规范

### 4.1 全局文档命名

全局文档统一放在 `00_全局工作台`：

- `00_全局工作台.md`：总入口、总规则、目录结构、文档使用规则
- `01_全局复利与踩坑日志.md`：记录错误、踩坑、弯路、复利方法
- `02_新项目SOP.md`：新项目创建和执行流程

### 4.2 项目文件夹命名

项目文件夹统一放在 `10_项目档案`：

```text
project-三位编号-项目名称
```

示例：

```text
project-001-字节投流
project-002-小红书投放复盘
project-003-私域成交SOP
```

编号规则：

- 从 `001` 开始。
- 每新增一个项目，编号递增。
- 编号一旦创建，不因项目结束、暂停、删除而复用。
- 项目名称要短、清晰、能一眼识别主题。

### 4.3 项目内部文档命名

项目内部优先使用固定目录：

- `00_项目总览.md`
- `01_需求与目标`
- `02_执行过程`
- `03_素材与资料`
- `04_交付物`
- `05_复盘与沉淀`

过程类文件建议使用：

```text
YYYY-MM-DD_主题.md
```

示例：

```text
2026-07-04_首次需求梳理.md
2026-07-04_执行记录.md
2026-07-04_问题复盘.md
```

### 4.4 仓库级文档命名

长期代码项目允许在 Workspace 根目录保留仓库级文档：

- `README.md`：项目介绍、启动方式、核心规则、验证命令。
- `AGENTS.md`：Codex 固定工作规则、安全红线、开工前必读文件。
- `MIGRATION_NOTES.md`：阶段迁移说明。
- `V版本号_ACCEPTANCE.md`：版本验收记录，例如 `V0.1_ACCEPTANCE.md`、`V0.1.1_ACCEPTANCE.md`。

长期交接文档统一放在 `docs`：

- `CODEX_HANDOFF.md`：给 Codex 的交接入口。
- `PROJECT_STATE.md`：项目当前状态。
- `CURRENT_TASK.md`：当前任务与下一步。
- `DECISION_LOG.md`：架构与产品决策日志。
- `DEPLOYMENT_STATE.md`：部署、环境和运行状态。
- `ROADMAP.md`：路线图。
- `SAFETY_BOUNDARY.md`：安全边界和禁止事项。

### 4.5 Git 提交命名

提交信息统一使用：

```text
类型: 简短说明
```

常用类型：

- `feat`：新增功能或版本能力。
- `fix`：修复问题。
- `docs`：文档更新。
- `chore`：工程配置、依赖、结构调整。
- `refactor`：不改变行为的代码重构。
- `test`：测试补充或调整。

示例：

```text
feat: 完成 v0.1.1 数据复核与安全闭环
docs: 更新全局工作台规则
chore: 重构为 pnpm 工作区结构
```

## 5. 各文档使用规则

### 5.1 `00_全局工作台.md`

用途：

- 作为 Workspace 的总入口。
- 汇总所有全局规则。
- 记录当前目录结构和命名规范。
- 给 Codex 提供长期行为约束。

更新规则：

- 当目录结构、命名规范、项目管理方式发生变化时，必须更新。
- 不记录单个项目的细节，项目细节进入对应项目文件夹。

### 5.2 `01_全局复利与踩坑日志.md`

用途：

- 记录犯过的错误。
- 记录踩过的坑。
- 记录走过的弯路。
- 沉淀以后可以复用的方法、检查清单、标准动作。

更新规则：

- 只追加，不删除历史记录。
- 每条记录必须包含：日期、项目、问题、原因、修正动作、可复用方法。
- 如果某个坑属于具体项目，同时也要在项目的 `05_复盘与沉淀` 中记录。

### 5.3 `02_新项目SOP.md`

用途：

- 作为以后所有项目的启动标准流程。
- 明确项目编号、目录创建、资料归档、交付归位规则。

更新规则：

- 每次发现更好的项目执行流程时，可以更新 SOP。
- SOP 变化后，需要同步检查《全局工作台》中的目录结构和规则是否也要更新。

### 5.4 `AGENTS.md`

用途：

- 作为当前代码仓库内 Codex 的项目级强约束。
- 明确技术栈、包结构、安全红线、开工前必读文件和完成后更新规则。

更新规则：

- 当项目定位、技术栈、目录结构、安全红线、必读文档发生变化时，需要更新。
- 如果 `AGENTS.md` 与全局工作台冲突，先遵守更具体、更接近当前项目的 `AGENTS.md`，再补充更新全局文档。

### 5.5 `docs` 交接文档

用途：

- 让长期项目可以跨会话、跨阶段连续推进。
- 记录当前任务、项目状态、决策、部署状态、路线图和安全边界。

更新规则：

- 每完成一个阶段版本，需要更新 `PROJECT_STATE.md` 和 `CURRENT_TASK.md`。
- 有架构或产品方向决策时，需要更新 `DECISION_LOG.md`。
- 有部署、数据库、环境变量、端口、运行方式变化时，需要更新 `DEPLOYMENT_STATE.md`。
- 有安全边界变化时，需要更新 `SAFETY_BOUNDARY.md`。
- `docs` 文件如已有未提交修改，必须先阅读，不得覆盖用户或其它流程的改动。

### 5.6 Git 版本管理

用途：

- 保存本地版本快照。
- 支持查看历史、对比差异、必要时回退。
- 为后续推送 GitHub 或创建远程备份做准备。

执行规则：

- 提交前先运行 `git status --short`。
- 提交前查看 `git diff --stat` 或 `git diff --cached --stat`。
- 提交前检查 `.env`、token、密钥、cookie、authorization、数据库文件、构建产物是否被误加。
- 只在用户要求提交或任务需要保存版本时提交。
- 当前仓库如果 `git remote -v` 没有输出，说明没有配置 GitHub 远程仓库，提交只保存在本地。
- 配置远程并执行 `git push` 后，才算同步到 GitHub。
