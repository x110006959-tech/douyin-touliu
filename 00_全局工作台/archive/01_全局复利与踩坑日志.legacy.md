# 全局复利与踩坑日志

## 2026-09-19｜project-001-字节投流｜展示优化不能冒充分析质量改善

- 问题：用户反馈报告没有价值，初稿用前端比值和泛化结论覆盖服务端主卡；测试样例额外提供了生产 DTO 不返回的订单字段，且未核验期间。
- 原因：把“可信单个指标”误当成“可组合比较的一组指标”，把排版与算术解释误当成 AI 分析改进。
- 修正：恢复服务端裁决优先，只解释服务端目标及冻结窗口比较；删掉跨指标推导；补充无效值、相等、零消耗、冲突复核和动作生命周期的渲染回归。测试总数按各包实际输出求和，本次为 785，不沿用历史的 764。
- 可复用方法：先验证真实契约和用户所需的信息增量，再决定实现层。展示改善、离线样例、真实模型质量及部署分别记账；未验证完整目标不得靠反复报告局部绿灯宣称完成。

## 2026-09-18｜project-001-字节投流｜候选终态必须连同来源、单位和业务口径一起原子化

- 问题：来源冲突选择 `DOM` 后，复核值、单位、精确值和可信状态都已改为 DOM 候选，但指标来源列、证据 `sourceType`、单位来源和业务口径仍是冲突前 API 来源；页面、汇总、审计、项目历史和后续诊断都会把这条人工确认指标继续表达成 API 口径。
- 原因：候选投影只关注“数值和单位”，没有把来源标识、证据类型、单位来源和业务口径纳入同一终态；`MetricSourceCandidate` 原先也不携带这些字段，选择 DOM 时无法恢复 DOM 证据的真实口径。
- 修正动作：候选类型增加 `unitSource`、`scope`、`scopeExplicit`，API 与 DOM 候选在生成时分别保留自己的单位来源与业务口径；来源冲突持久化同时写 `metricSource`、`metricUnit`、`scope`、`rawEvidence.sourceType`、`sourceStatus`、`unitSource`、`semanticScope`，单条和 bulk 复核都同步更新复核层与快照层。
- 补充收口：只有 `scopeExplicit === true` 时才把候选 `scope` 写入最终业务口径；候选因缺少显式语义口径而回退成指标键时，不再把 `gmv`、`spend` 等键名伪装成真实 `semanticScope`，而是让下游按路线与指标名重新推断。
- 可复用方法：凡是从多候选中选择最终来源的人工决策，都不能只持久化“值 + 单位”；必须把来源标识、证据类型、单位来源和业务口径等全部可派生属性作为同一终态原子更新，避免后续链路仍看到“已选 B，但来源仍是 A”。

## 2026-09-18｜project-001-字节投流｜部署校验不能把 grep -q 的空输出当成失败

- 问题：本机部署脚本首次执行时，Web 制品检查命令使用 `grep -q`，成功时标准输出为空；脚本误把空字符串判断为检查失败，触发整套容器回退。
- 原因：命令行校验脚本混用了“命令退出码”和“标准输出是否为空”两种成功判断；`grep -q` 的正确成功信号是退出码 `0`，不是输出文本。
- 修正动作：只依赖 Docker 命令非零退出码来判定该制品检查失败，不再要求 `grep -q` 产生输出；回退后确认旧服务恢复，再重试完成切换。
- 可复用方法：部署或运维脚本中，使用 `-q`、`--quiet`、`test` 等只靠退出码表达结果的命令时，不能再用输出字符串长度作为成功条件；应统一让子进程异常抛出，成功时不检查输出。

## 2026-09-17｜project-001-字节投流｜人工选择候选必须一次改写所有证据层

- 问题：来源冲突字段选择 `API` 或 `DOM` 后，复核行显示的值变了，但正式证据里的 `normalizedValue/displayValue/fieldLabel/timeRange` 仍指向冲突前候选；底层快照指标也还是 `SOURCE_CONFLICT + INVALID`，后续诊断和总览可能继续使用旧候选。
- 原因：候选选择被当成只更新 `reviewedValue` 的派生动作，没有把“人工选择”定义为对同一业务指标全部证据层的原子修正；来源冲突和忽略只在其中一层被处理。
- 修正动作：抽出 `sourceConflictReviewPersistence`，单条与 bulk 复核都把选定候选同时写入 `ReviewedMetric` 和对应 `NormalizedMetric`，包括单位、展示值、归一化值、字段标签、周期、来源状态和可信状态；忽略分支仍只做排除，不产生候选值。回归用 API `1200` / DOM `1300` 分别通过单条和 bulk 选择 DOM，验证复核证据、快照证据和正式诊断输入都为 `1300`。
- 补充收口：`toReviewedMetricDTO.normalizedValue` 改为优先读取当前证据的 `normalizedValue`，避免人工选择后页面精确值仍显示旧候选或“数据缺失”。
- 可复用方法：凡是有多个候选值的人工选择终态，都必须定义一条“从选择结果到所有派生证据层”的同一更新路径；不要只改 UI 或复核派生字段，让底层证据继续表达未选择状态。

## 2026-09-17｜project-001-字节投流｜“忽略”要贯穿到证据底层的同一主体

- 问题：来源冲突字段忽略后，复核行已为 `IGNORED`，但真实采集快照里的同主体 `normalizedMetrics.rawEvidence` 仍是 `SOURCE_CONFLICT + INVALID`；快照级门禁继续把这条证据当不可信，正式诊断仍可能被阻断。
- 原因：忽略动作只改了派生复核状态，没有把同一业务主体的底层证据从后续门禁中一并移除；回归测试还只更新了复核行，没有使用真实快照证据形态。
- 修正动作：诊断输入与就绪检查都按 `normalizedMetricId` 排除 `IGNORED` 指标对应的快照证据；批量确认审计的无效证据计数排除来源冲突指标，避免双计。回归同步改写快照 `normalizedMetric.rawEvidence` 到真实冲突失效状态。
- 可复用方法：任何“忽略/排除”终态都必须定位到同一业务主体的所有证据层，并在每一层使用同一标识集合移除；回归数据要复制真实生产形态，不能只改方便测试的派生对象。

## 2026-09-17｜project-001-字节投流｜解除配对不能只删凭证，必须清空账号/任务作用域状态

- 问题：插件“解除配对”只删 token、配置、上下文和实时脉冲状态，旧页面活动、本地快照、路线上传状态和采集日志仍留在本地；之后换账号配对时，旧账号页面 URL 和任务状态可能继续出现在新会话。任务切换也会保留旧页面活动。
- 原因：把“凭证失效”与“账号/任务作用域状态失效”混在一起，没有为本地存储建立统一清理边界。
- 修正动作：解除配对统一清理全部账号/任务相关本地状态后只追加一条新的解绑日志；凭证失效后重新配对也先清旧页面活动和日志，并在当前无活动实时脉冲时清除三份 live pulse 持久化状态；任务切换补齐旧页面活动清理并避免使用旧活动发心跳；重新选择当前任务直接返回，不误清运行中的实时脉冲。
- 可复用方法：任何“解绑、退出、切换账号/任务”动作都要先列出该身份/任务作用域下的全部持久化状态并统一清理，不能只删主凭证；清理后如果还要写审计日志，应在新会话写入而不是先删再补旧日志。

## 2026-09-17｜project-001-字节投流｜批量确认必须显式排除需要逐项选择的状态

- 问题：任务级“确认全部”把 `SOURCE_CONFLICT` 待复核指标也改成 `CONFIRMED`，但来源冲突字段实际仍要求用户逐项选择 API、DOM 或 IGNORE，形成“已确认但未选择来源”的矛盾记录；同口径复核还发现 `INVALID` 证据也不能按原值自动确认。
- 原因：批量操作直接枚举全部 `PENDING`，没有区分“可安全按原值确认”和“必须保留人工选择/处理”的状态；后续正式诊断虽然会再过滤无效证据，但复核状态已经失真。
- 修正动作：抽出 `taskLevelConfirmableReviewedMetrics`，批量确认使用与逐项确认相同的 `canConfirmMetric` 门禁，只处理非冲突且非无效的 `PENDING` 指标；冲突和无效字段保持 `PENDING`，审计分别记录被阻止数量；前端文案按服务端返回区分全部成功与部分成功。
- 可复用方法：任何任务级批量确认/审批，都要先定义可自动通过的最小状态子集，并复用逐项确认的同一门禁；把需要逐项决策或处理的状态显式排除并计数，不能把“最终决策会过滤”当作复核状态可以提前失真的理由。

## 2026-09-17｜project-001-字节投流｜“忽略”不是“不可信证据”

- 问题：来源冲突字段选择“忽略”后，复核状态为 `IGNORED`，但底层证据为让该字段退出正式数据被标记为 `INVALID`；诊断构造与就绪判断继续把这份已忽略指标当作不可信证据，导致正式诊断被错误阻断。
- 原因：复核状态和证据有效性被混在同一个不可信判断里，没有先排除“用户已明确忽略”的指标；字段级忽略应当从可用证据中移除，而不是变成新的阻塞项。
- 修正动作：在 `buildDecisionInput` 与 `hasUntrustedCurrentEvidence` 的不可信证据检查中排除 `reviewStatus === "IGNORED"`；已忽略指标仍不进入可用证据，但不再阻塞诊断。
- 可复用方法：任何“忽略/排除”终态都要在后续门禁中先行从待处理与风险集合移除，不能只从可选值集合移除；否则容易把用户的明确排除重新解释为数据异常。

## 2026-09-17｜project-001-字节投流｜认证状态旧回调不能覆盖新会话

- 问题：退出请求异步发送，旧 `.finally` 在新登录完成后执行，会把新 CSRF、token 和 user 清空；登录后补读 `/auth/me` 的旧响应也可能覆盖随后的退出状态。
- 原因：只有积分刷新用了 latest-request 守卫，认证状态本身没有区分“旧异步结果”和“当前会话过渡”。
- 修正动作：为认证状态增加单调递增的过渡版本，初始恢复、登录/注册、退出开始时递增；旧回调只有在版本仍当前时才写回，积分刷新守卫同步失效。登录失效跳转同时等待撤销请求收尾，并用稳定回调避免无关 `user` 更新触发认证副作用重新执行。补读 `/auth/me` 失败时同步清空整套认证状态，避免半登录残留。
- 可复用方法：任何可被用户连续操作覆盖的客户端会话状态，都要用会话代次或过渡版本隔离旧异步结果；不能只保护某个派生字段，而要保护状态源本身。

## 2026-09-08｜project-001-字节投流｜自由文本脱敏不能只覆盖已有关键词

- 问题：失败步骤日志最初只识别常见 token/cookie/password、标准 URL 和联系方式；PAT、云 AccessKey、长账号标识及姓名仍可能原样保存。
- 原因：复用了面向既有结构化字段的脱敏器，但新记录是外部模型生成的自由文本，Schema 通过只能证明结构与长度，不能证明内容安全。
- 修正：在保存前增加高风险整条抑制，覆盖常见凭证前缀、长不透明标识、账号/身份字段、联系方式和 URL；只保留定位门禁必需的普通业务语义。加入反例与保留语义回归，再进行候选和运行态验证。
- 可复用方法：任何新增自由文本日志都应先用凭证、身份、URL 和长标识反例验证，不能把“调用了通用 sanitizer”等同于“不会泄露”；安全补强应在首次部署前完成，不靠线上日志试错。

## 2026-08-26｜project-001-字节投流｜停止后的实时采集结果必须保留来源作用域

- 场景：用户点击启动 API 持续采集后，Popup 短暂显示“已开启”，按钮却回到“开始”；后台会话实际可能已经因首轮失败或页面事件停止。
- 问题：停止态只返回 `lastOutcome`，Popup 为防止跨标签串状态又要求路线和标签页匹配，导致没有来源作用域的失败结果被过滤，旧成功提示覆盖了真实失败。
- 修正动作：停止结果保存脱敏的路线与标签页 ID；Popup 只在当前路线和当前标签页匹配时显示该结果，同时用渲染代次和动作锁隔离旧异步回写。
- 可复用方法：任何跨页面长会话的停止结果都必须携带最小来源作用域；状态过滤不能只靠业务任务 ID，也不能用成功 Toast 覆盖后台最终状态。

## 2026-08-26｜project-001-字节投流｜登录失效必须提供可完成的回登录动作

- 问题：工作台接口返回登录失效时只展示错误文字；即使补充客户端路由，异步清理会话也可能让登录页读到旧状态并跳回工作台。
- 原因：认证失效提示与登录入口脱节，且会话注销请求不是同步完成。
- 修正动作：仅对明确的 `UNAUTHORIZED` 展示返回登录按钮，点击时先触发会话清理，再使用安全回跳地址硬跳转登录页；通用认证失效页统一使用按钮样式。
- 可复用方法：所有登录失效错误都应提供明确回登录动作；如果会话清理异步，不能只依赖客户端路由切换。

## 2026-08-10｜project-001-字节投流｜Schema 漂移不能用“失败关闭”代替最小兼容

- 场景：直播商品页 API 在 Extension 内容脚本中被记录为 `SCHEMA_MISMATCH`，因此脉冲在上传前停止，服务端与任务大屏都没有实时帧；Popup 却因状态被清空继续显示等待下一节拍。
- 问题：把响应对象设为严格禁止新增字段，会将平台安全新增的元数据、等价状态外层或暂时为 `null` 的单项指标误判为不可信；同时失败状态未进入控制面，现场无法区分“尚未到节拍”和“已停止未上传”。
- 影响：用户可能反复尝试或用正式快照绕过实时链路，服务端日志又无法提供失败端点，导致排查方向偏离。
- 根因：契约同时承担“最小数据投影”和“完整响应封闭性”，没有区分允许忽略的新增结构与真正未知包装；实时会话停止后仅保留内存状态。
- 修正动作：只接受明确的等价外层，允许对象内新增字段后立即剥离，继续按固定白名单投影；`null` 只代表缺失值。持久化按任务隔离的最小失败摘要（原因、端点、时间），Popup 轮询展示，并在新会话、任务切换或解除配对时清除。
- 可复用方法：对外部 API 契约采用“严格外层/白名单投影/可忽略对象新增字段”的三层模型。任何失败关闭流程都要把脱敏的失败原因带到用户控制面，并明确是否请求已到服务端。
- 是否需要更新 SOP：建议在浏览器采集验收中增加“新增无关字段、等价响应包装、null 指标、失败端点即时可见、跨任务错误不串台”用例。

## 2026-08-25｜project-001-字节投流｜扩展重载后必须刷新目标页面再启动跨脚本流程

- 场景：用户在巨量本地推页面看到 API 持续采集连续失败 `3/3` 后自动中断，最后原因只有通用的 `PULSE_CAPTURE_FAILED`。
- 问题：Service Worker 随扩展重载升级，但已打开的目标后台页仍保留旧 Content Script。跨脚本协作缺少构建一致性断言时，首轮失败会被泛化，三连失败保护再按设计停止。
- 影响：用户无法区分“平台 API 请求失败”和“目标页面尚未刷新”，容易重复启动采集，却没有获得可行动的失败原因。
- 根因：此前只在网页桥接路径识别扩展重载失效，没有把同一原则应用到 Popup -> Content Script -> Service Worker 的本地推启动路径。

- 可复用方法：凡是扩展重载后依赖已注入页面脚本的流程，启动时都要校验页面脚本与后台构建一致；刷新是有效修复动作时，UI 必须在开始前明确提示，而不是依靠运行期通用失败兜底。
- 是否需要更新 SOP：建议在本地扩展验收清单加入“重载扩展后不刷新目标页”的反向用例。
