# 全局复利与踩坑日志

生效日期：2026-07-04

用途：记录犯过的错误、踩过的坑、走过的弯路，以及未来可以持续复用的方法。

## 使用规则

1. 只追加，不删除历史记录。
2. 每次出现错误、返工、文件散落、路径混乱、命名不清、流程重复摸索时，都要记录。
3. 每条记录必须写清楚：日期、项目、问题、原因、修正动作、可复用方法。
4. 如果问题属于具体项目，也要同步记录到该项目的 `05_复盘与沉淀`。
5. 能转化为 SOP 的经验，要反向更新《新项目SOP》或《全局工作台》。

## 2026-08-11｜project-001-字节投流｜非必要端点不能绑定实时会话成败

- 场景：实时 API 在商品分栏的整分钟同时读取 `key_index` 与 `room_minute_indicator`；后者发生 `SCHEMA_MISMATCH` 后，整个会话在上传前停止，任务大屏没有任何实时帧。
- 问题：分钟趋势不是实时卡片的必要数据，却被调度为实时会话的阻断依赖；仅兼容它的未知响应结构会让实时链路继续依赖不稳定端点。
- 根因：早期固定节拍设计把“整分钟刷新趋势”实现为 PULSE 的附加请求，而没有按数据用途隔离采集责任。
- 修正动作：PULSE 固定只请求 `key_index`；分钟趋势收回到用户主动 SNAPSHOT，并在服务端拒绝任何 PULSE 分钟行。Popup 同步呈现具体失败端点及停止状态。
- 可复用方法：长会话中，只有完成该会话核心目标所必需的输入可以成为失败关闭依赖。展示性、低频或正式证据类数据应拆入独立、显式流程，并在服务端拒绝跨用途夹带。
- 是否需要更新 SOP：建议把“实时链路端点最小集和非必要端点隔离”加入采集方案评审清单。

## 2026-08-11｜project-001-字节投流｜失败关闭后的控制面必须与后台状态同源

- 场景：实时 API 因 `THREE_CONSECUTIVE_FAILURES` 已停止，Popup 文案显示“已停止”，但按钮仍显示“停止 API 持续采集”。
- 问题：后台状态和控制面分两条刷新路径，轮询只刷新说明文字，导致用户无法确认是否可以重新启动。
- 根因：首次 `render()` 写入按钮，后续 `refreshLivePulseStatus()` 只写入状态文案。
- 修正动作：抽出纯状态函数统一计算按钮文案和 disabled 门禁；每次轮询依据最新 `GET_STATE.livePulse.active` 同步按钮，并保留配对/API 开关门禁。
- 可复用方法：任何可自动失败关闭的长会话，都必须让状态文案、控制按钮和可用性来自同一份服务端/Worker 状态；回归要覆盖“运行中 → 失败停止 → 可重新启动”。
- 是否需要更新 SOP：建议加入实时采集控制面一致性验收项。

## 2026-08-14｜project-001-字节投流｜新证据层放行必须同步所有门禁

- 场景：`decision-runs` 创建阶段已经允许直播概览 `REALTIME_API` 输入，但 AI Worker 执行时的诊断技能审计仍硬编码要求 `REVIEWED_METRIC`，导致排队成功后运行失败为 `DECISION_NOT_READY`。
- 问题：同一条业务能力被多个门禁表达，新增证据层只改了入口和 readiness，没有同步诊断技能审计和证据目录语义。
- 影响：用户看到实时 API 已可创建诊断运行，却仍被旧“人工复核快照层”拦住，体验上等同于旧快照确认流程被带回。
- 根因：早期把“正式诊断证据”近似成“人工复核指标层”，后来加入服务端可信实时 API 后没有抽出统一判定。
- 修正动作：将诊断技能审计改为“正式证据层”：人工复核快照或受限直播概览实时 API 二选一；Worker 只复用确认为 `LIVE_DATA_SCREEN` 实时 API 的 stored input，并补回归测试覆盖无快照 Worker 执行。
- 可复用方法：新增证据层、状态层或认证层时，必须同步检查创建入口、后台 Worker、规则引擎、AI 审计、证据目录、前端口径和回归测试；不能用其中一个门禁通过代替端到端通过。
- 是否需要更新 SOP：建议把“多门禁一致性清单”加入采集/诊断类项目评审。

## 2026-07-04｜project-001-字节投流｜全局项目管理规则此前未落地

- 场景：当前 Workspace 原本只有 `.git`，没有全局工作台、项目 SOP、复利日志，也没有当前项目的标准项目文件夹。
- 问题：如果继续执行项目，后续资料、过程记录、交付物容易散落，难以复用和复盘。
- 影响：项目越多，查找成本越高；重复踩坑概率增加；Codex 后续执行缺少统一约束。
- 根因：缺少一个 Workspace 级别的统一入口和强制目录规范。
- 修正动作：创建 `00_全局工作台`、`10_项目档案`，并为当前项目创建 `project-001-字节投流`。
- 可复用方法：以后每个新项目开始前，先创建 `project-三位编号-项目名称` 文件夹，再把需求、过程、素材、交付、复盘全部放入该项目目录。
- 是否需要更新 SOP：已纳入《新项目SOP》。

## 2026-07-08｜project-001-字节投流｜Git 本地提交与 GitHub 同步容易混淆

- 场景：项目已经多次执行 `git commit`，但仓库没有配置远程地址。
- 问题：容易把“本地 Git 提交”误以为“已经提交到 GitHub”。
- 影响：如果电脑本地数据丢失，未推送的 Git 提交不会自动存在于 GitHub；协作方也无法看到这些版本。
- 根因：没有明确区分 `git commit` 与 `git push` 的边界，也没有在全局文档中写清楚远程状态检查方式。
- 修正动作：在《全局工作台》和《新项目SOP》中补充 Git 版本管理规则，明确 `git remote -v` 无输出时代表没有配置 GitHub 远程仓库。
- 可复用方法：每次用户问“提交到哪里”或要求提交版本时，先说明：`git commit` 是本地版本，`git push` 才是推送远程；提交后同步检查 `git status --short`、`git log --oneline -n 3`、`git remote -v`。
- 是否需要更新 SOP：已更新。

## 2026-07-10｜project-001-字节投流｜测试产物和包内脚本被宽泛 Gitignore 吞掉

- 场景：源码与测试均能在本机运行，但 `dist` 测试被重复执行，包内 `scripts` 目录又不会出现在 Git 状态中。
- 问题：宽泛的 `scripts/` 与历史构建产物会让关键构建脚本漏提交，并让 Vitest 同时运行源码和过期编译测试。
- 影响：本机“能跑”无法保证干净环境可复现，失败数量会被重复放大。
- 根因：忽略规则没有限定仓库根目录，构建前也没有清理输出目录，测试命令没有限定源码目录。
- 修正动作：把忽略规则收窄为 `/scripts/`，包内脚本进入 Git 跟踪；测试限定 `src`，构建前清理 `dist`，API 测试自动创建并销毁临时数据库。
- 可复用方法：新增通用目录忽略规则时先运行 `git check-ignore -v` 验证包内同名目录；编译型项目的测试命令必须排除产物目录。
- 是否需要更新 SOP：后续把 Gitignore 跟踪验证纳入新项目初始化检查表。

## 2026-07-10｜project-001-字节投流｜中文工作区触发 Docker BuildKit 会话头错误

- 场景：Dockerfile 和 Compose 配置校验通过，但 Windows Docker Desktop 在中文工作区执行 BuildKit 构建时报告会话头含不可打印字符。
- 问题：默认 BuildKit 无法从当前中文路径发送构建上下文。
- 影响：本地镜像验证被阻断，但服务器英文路径部署不受影响。
- 根因：Docker Desktop/BuildKit 对 Windows 非 ASCII 路径的会话元数据兼容问题。
- 修正动作：本地验证临时设置 `DOCKER_BUILDKIT=0` 与 `COMPOSE_DOCKER_CLI_BUILD=0`，镜像和完整 Compose 均成功验证。
- 可复用方法：优先把容器项目放在 ASCII 路径；遇到该错误先验证 Compose 配置，再用兼容构建模式区分路径问题与 Dockerfile 问题。
- 是否需要更新 SOP：建议在 Windows Docker 项目规范中增加 ASCII 工作区建议。

## 2026-07-10｜project-001-字节投流｜源码已修复但发布包仍携带旧代码

- 场景：Extension 源码和 `dist` 已改为安全 XHR 原型补丁，但 Git 跟踪的 unpacked 目录和两个发布 ZIP 仍整体替换 `window.XMLHttpRequest`。
- 问题：只测试源码会产生“代码安全、用户安装包不安全”的假通过。

- 根因：build、release 和最终制品测试彼此分离，发布目录没有由当前源码自动生成。
- 修正动作：build 自动同步 unpacked 目录，release 只保留当前版本 ZIP，测试直接解压 ZIP 校验版本和安全边界。
- 可复用方法：浏览器插件、桌面包和容器镜像都必须对最终制品做安全测试，不能只验证源文件。
- 是否需要更新 SOP：应把“最终发布物校验”加入所有有构建制品项目的验收清单。

## 2026-07-24｜project-001-字节投流｜页面“无法识别”必须先区分规则缺失与未触发采集

- 场景：用户反馈两个已打开的后台页面无法识别，但源码和插件制品已包含对应精确路径的路线规则。
- 问题：仅从页面现象判断会把“尚未产生快照”误当成“路线识别失败”。
- 影响：容易为不存在的识别问题增加宽泛权限或自动采集，扩大安全面且不能解决真实问题。
- 根因：旧任务中的两个路线均为待确认，且无失败码、无快照；用户未通过 Popup 完成一次确认采集。
- 修正动作：以路线规则、制品、任务路线状态和快照记录交叉核验；明确域名授权、路线识别与用户确认上传三层职责。
- 可复用方法：排查采集问题时先确认“规则是否存在、用户是否触发、服务端是否接收、快照是否写入”四个事实，不因空数据放宽域名、自动点击或自动上传边界。
- 是否需要更新 SOP：建议将四段式采集排查加入带浏览器插件项目的验收清单。

## 2026-07-24｜project-001-字节投流｜一次用户确认需要服务端可验证的信任链

- 场景：Popup 在路线识别失败时允许用户选择本次路线并点击采集，但 API 将所有 `manuallyConfirmed` 都标为待确认，造成同一操作需要二次确认。
- 问题：直接信任客户端布尔值会让非插件或伪造请求绕过路线确认；完全不信任又破坏已确认的产品流程。
- 影响：用户体验与服务端可信边界无法同时成立。
- 根因：此前状态机没有区分 Extension 凭证采集和网页/手工入口的“人工确认”语义。
- 修正动作：只对 Extension 凭证、账号任务归属、精确可信 HTTPS 来源、已配置路线和无冲突证据同时成立的请求，将本次 Popup 选择写为 `VERIFIED`；其他入口保持待人工确认，非可信来源直接拒绝。
- 可复用方法：把客户端确认拆成“用户意图”和“服务端可验证上下文”；只有两者同时成立才能改变受信状态，不以 UI 字段作为权限或证据的唯一来源。
- 是否需要更新 SOP：建议纳入所有涉及浏览器插件、移动端或第三方客户端确认动作的状态机审查。

## 2026-07-25｜project-001-字节投流｜只在决策读取时过滤旧证据不足以保证校准一致性

- 场景：正式诊断已经排除旧快照，但标准指标校准接口仍可对历史指标写入，而表格单元格校准已有当前快照和版本门禁。
- 问题：读取侧安全不能替代写入侧一致性；旧页面可能留下不符合当前采集证据的复核记录，用户也无法从界面判断该记录已失效。
- 影响：虽然不会进入正式决策，审计和校准流程仍会产生混乱，并可能导致不同复核入口的并发语义不一致。
- 根因：标准指标复用的旧复核接口早于任务专属大屏，缺少快照版本作为写入令牌。
- 修正动作：统一指标和表格的当前快照、账号/路线确认、版本检查与 Serializable 冲突处理；任何校准成功都推进快照版本，前端读取最新版本后再提交。
- 可复用方法：涉及“原始事实 + 人工校准 + 正式判断”的链路，应同时检查读取门禁和写入门禁；不能以“最终不会使用”代替并发、审计和用户可理解性约束。
- 是否需要更新 SOP：建议在涉及可复核证据的项目验收清单中增加“写入是否带当前版本令牌、不同校准入口是否共享语义”。

## 2026-07-25｜project-001-字节投流｜汇总去重不能跨越业务路线

- 场景：任务校准大屏需要汇总直播概览、本地推总览和任务列表等多条路线的指标。
- 问题：标准指标此前只按指标名去重，导致不同路线的同名真实指标（例如“消耗”）只显示一条。
- 影响：用户无法逐路线校准完整证据，可能误以为某个页面没有采集到数据。
- 根因：将用于同一快照内部归并的标准指标键错误地复用于跨路线汇总。
- 修正动作：汇总去重键加入路线；同一路线内继续归并，同名指标跨路线保留独立来源、时间和复核状态；用真实 API 集成流程增加回归覆盖。
- 可复用方法：多来源汇总前先确认数据的业务身份是否包含来源维度；展示层去重不得抹去后续复核、审计或决策所需的证据边界。
- 是否需要更新 SOP：建议在多来源数据看板验收清单中增加“同名字段跨来源同时存在”的回归用例。

## 2026-07-26｜project-001-字节投流｜登录页不应被通用请求超时长期阻塞

- 场景：隔离测试 Web 的 API 曾短暂未启动，用户刷新登录页后持续看到“正在确认登录状态…”。
- 问题：认证初始化复用了 20 秒业务请求超时，失败前没有可操作的回落界面，用户很难判断是在检查会话还是页面已失效。
- 影响：本地验收被无意义阻塞，容易把环境启动顺序问题误判为登录功能故障。
- 根因：首次会话确认与普通数据请求共享同一超时策略。
- 修正动作：为 `/auth/me` 初始化增加独立 3 秒中止控制器；超时、网络失败或无会话均尽快进入登录表单，组件卸载时取消请求。
- 可复用方法：把应用启动必需的身份探测与可延迟的业务请求分开设定超时和回退；重启本地服务后必须用浏览器验证水合完成，而不只检查 API 就绪接口。
- 是否需要更新 SOP：建议纳入本地多服务验收清单。

## 2026-07-27｜project-001-字节投流｜数据保留升级必须先验证备份可恢复

- 场景：用户需要在保留原登录账号和历史采集数据的本地环境中体验新版本。
- 问题：仅确认备份文件存在不能证明其可用于恢复；Windows 终端还可能在二进制重定向时损坏数据库归档。
- 影响：未经恢复验证就迁移会让用户对历史账号和业务数据失去保护信心。
- 根因：直接将 `pg_dump` 二进制输出重定向到 PowerShell 文件流，会产生编码损坏；而原环境与隔离验收库又存在明确的数据边界。
- 修正动作：在 PostgreSQL 容器内生成 custom-format dump，再二进制复制到本地；计算 SHA-256，并恢复到独立临时 PostgreSQL，确认业务表与迁移记录后才执行加法迁移。
- 可复用方法：涉及用户历史数据的本地升级，固定执行“迁移前计数 -> 可恢复备份 -> 独立恢复验证 -> 加法迁移 -> 数据计数与接口复验”；环境入口必须明确标出原数据环境与隔离验收环境。
- 是否需要更新 SOP：建议纳入数据库迁移与本地预上线切换清单。

- 问题：把响应对象设为严格禁止新增字段，会将平台安全新增的元数据、等价状态外层或暂时为 `null` 的单项指标误判为不可信；同时失败状态未进入控制面，现场无法区分“尚未到节拍”和“已停止未上传”。
- 影响：用户可能反复尝试或用正式快照绕过实时链路，服务端日志又无法提供失败端点，导致排查方向偏离。
- 根因：契约同时承担“最小数据投影”和“完整响应封闭性”，没有区分允许忽略的新增结构与真正未知包装；实时会话停止后仅保留内存状态。
- 修正动作：只接受明确的等价外层，允许对象内新增字段后立即剥离，继续按固定白名单投影；`null` 只代表缺失值。持久化按任务隔离的最小失败摘要（原因、端点、时间），Popup 轮询展示，并在新会话、任务切换或解除配对时清除。
- 可复用方法：对外部 API 契约采用“严格外层/白名单投影/可忽略对象新增字段”的三层模型。任何失败关闭流程都要把脱敏的失败原因带到用户控制面，并明确是否请求已到服务端。
- 是否需要更新 SOP：建议在浏览器采集验收中增加“新增无关字段、等价响应包装、null 指标、失败端点即时可见、跨任务错误不串台”用例。
