# 全局复利与踩坑日志

生效日期：2026-07-04

用途：记录犯过的错误、踩过的坑、走过的弯路，以及未来可以持续复用的方法。

## 使用规则

1. 只追加，不删除历史记录。
2. 每次出现错误、返工、文件散落、路径混乱、命名不清、流程重复摸索时，都要记录。
3. 每条记录必须写清楚：日期、项目、问题、原因、修正动作、可复用方法。
4. 如果问题属于具体项目，也要同步记录到该项目的 `05_复盘与沉淀`。
5. 能转化为 SOP 的经验，要反向更新《新项目SOP》或《全局工作台》。

## 记录模板

```text
## YYYY-MM-DD｜project-编号-项目名称｜问题标题

- 场景：
- 问题：
- 影响：
- 根因：
- 修正动作：
- 可复用方法：
- 是否需要更新 SOP：
```

## 2026-07-04｜project-001-字节投流｜全局项目管理规则此前未落地

- 场景：当前 Workspace 原本只有 `.git`，没有全局工作台、项目 SOP、复利日志，也没有当前项目的标准项目文件夹。
- 问题：如果继续执行项目，后续资料、过程记录、交付物容易散落，难以复用和复盘。
- 影响：项目越多，查找成本越高；重复踩坑概率增加；Codex 后续执行缺少统一约束。
- 根因：缺少一个 Workspace 级别的统一入口和强制目录规范。
- 修正动作：创建 `00_全局工作台`、`10_项目档案`，并为当前项目创建 `project-001-字节投流`。
- 可复用方法：以后每个新项目开始前，先创建 `project-三位编号-项目名称` 文件夹，再把需求、过程、素材、交付、复盘全部放入该项目目录。
- 是否需要更新 SOP：已纳入《新项目SOP》。

## 2026-07-08｜project-001-字节投流｜Git 本地提交与 GitHub 同步容易混淆

- 场景：项目已经多次执行 `git commit`，但仓库没有配置远程地址。
- 问题：容易把“本地 Git 提交”误以为“已经提交到 GitHub”。
- 影响：如果电脑本地数据丢失，未推送的 Git 提交不会自动存在于 GitHub；协作方也无法看到这些版本。
- 根因：没有明确区分 `git commit` 与 `git push` 的边界，也没有在全局文档中写清楚远程状态检查方式。
- 修正动作：在《全局工作台》和《新项目SOP》中补充 Git 版本管理规则，明确 `git remote -v` 无输出时代表没有配置 GitHub 远程仓库。
- 可复用方法：每次用户问“提交到哪里”或要求提交版本时，先说明：`git commit` 是本地版本，`git push` 才是推送远程；提交后同步检查 `git status --short`、`git log --oneline -n 3`、`git remote -v`。
- 是否需要更新 SOP：已更新。

## 2026-07-08｜project-001-字节投流｜阶段演进后全局规则没有及时同步

- 场景：项目从初始文档工作台发展到 pnpm workspace、API、Web、Chrome Extension、decision-engine、交接文档和 v0.1.1 验收，但全局工作台仍停留在 2026-07-04 的初始目录。
- 问题：全局文档没有覆盖 `AGENTS.md`、`docs` 交接文档、Git 提交规则和当前项目结构。
- 影响：后续执行任务时，Codex 可能只看到旧的项目管理规则，忽略当前代码仓库的真实结构和长期交接流程。
- 根因：阶段提交完成后，没有把“项目形成的新规则”反向沉淀到全局工作台。
- 修正动作：更新《全局工作台》《新项目SOP》和本日志，补充仓库级文档、交接文档、Git 版本管理、当前项目状态。
- 可复用方法：每完成一个阶段版本或出现新的固定流程，除了更新项目内 `docs`，还要判断是否需要同步到 `00_全局工作台`。
- 是否需要更新 SOP：已更新。

## 2026-07-10｜project-001-字节投流｜测试产物和包内脚本被宽泛 Gitignore 吞掉

- 场景：源码与测试均能在本机运行，但 `dist` 测试被重复执行，包内 `scripts` 目录又不会出现在 Git 状态中。
- 问题：宽泛的 `scripts/` 与历史构建产物会让关键构建脚本漏提交，并让 Vitest 同时运行源码和过期编译测试。
- 影响：本机“能跑”无法保证干净环境可复现，失败数量会被重复放大。
- 根因：忽略规则没有限定仓库根目录，构建前也没有清理输出目录，测试命令没有限定源码目录。
- 修正动作：把忽略规则收窄为 `/scripts/`，包内脚本进入 Git 跟踪；测试限定 `src`，构建前清理 `dist`，API 测试自动创建并销毁临时数据库。
- 可复用方法：新增通用目录忽略规则时先运行 `git check-ignore -v` 验证包内同名目录；编译型项目的测试命令必须排除产物目录。
- 是否需要更新 SOP：后续把 Gitignore 跟踪验证纳入新项目初始化检查表。

## 2026-07-10｜project-001-字节投流｜中文工作区触发 Docker BuildKit 会话头错误

- 场景：Dockerfile 和 Compose 配置校验通过，但 Windows Docker Desktop 在中文工作区执行 BuildKit 构建时报告会话头含不可打印字符。
- 问题：默认 BuildKit 无法从当前中文路径发送构建上下文。
- 影响：本地镜像验证被阻断，但服务器英文路径部署不受影响。
- 根因：Docker Desktop/BuildKit 对 Windows 非 ASCII 路径的会话元数据兼容问题。
- 修正动作：本地验证临时设置 `DOCKER_BUILDKIT=0` 与 `COMPOSE_DOCKER_CLI_BUILD=0`，镜像和完整 Compose 均成功验证。
- 可复用方法：优先把容器项目放在 ASCII 路径；遇到该错误先验证 Compose 配置，再用兼容构建模式区分路径问题与 Dockerfile 问题。
- 是否需要更新 SOP：建议在 Windows Docker 项目规范中增加 ASCII 工作区建议。

## 2026-07-10｜project-001-字节投流｜源码已修复但发布包仍携带旧代码

- 场景：Extension 源码和 `dist` 已改为安全 XHR 原型补丁，但 Git 跟踪的 unpacked 目录和两个发布 ZIP 仍整体替换 `window.XMLHttpRequest`。
- 问题：只测试源码会产生“代码安全、用户安装包不安全”的假通过。
- 影响：用户加载旧 release 后仍可能破坏平台页面静态属性和运行行为。
- 根因：build、release 和最终制品测试彼此分离，发布目录没有由当前源码自动生成。
- 修正动作：build 自动同步 unpacked 目录，release 只保留当前版本 ZIP，测试直接解压 ZIP 校验版本和安全边界。
- 可复用方法：浏览器插件、桌面包和容器镜像都必须对最终制品做安全测试，不能只验证源文件。
- 是否需要更新 SOP：应把“最终发布物校验”加入所有有构建制品项目的验收清单。
