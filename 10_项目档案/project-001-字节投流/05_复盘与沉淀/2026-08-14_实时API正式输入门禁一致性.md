# 2026-08-14｜实时 API 正式输入门禁一致性

## 场景

直播概览实时 API 已能在 `decision-runs` 创建阶段生成 `REALTIME_API` 输入，但 AI Worker 执行时仍被诊断技能审计拦下，失败为 `DECISION_NOT_READY`，原因是旧审计规则只认可 `REVIEWED_METRIC`。

## 问题

同一条“正式 AI 输入”能力分散在多个门禁中表达：创建入口、Worker、readiness、诊断技能审计和证据目录。新增实时证据层时只改了入口与 readiness，没有同步后续审计层。

## 影响

用户可以看到实时 API 输入已排队，但后续仍要求旧的快照/人工复核路径，等同于把“保存为正式快照/确认路线”流程带回了直播概览实时链路。

## 根因

早期系统把“正式诊断证据层”近似等同为“人工复核指标层”。直播概览实时 API 后来成为服务端可信输入后，没有抽出统一语义，导致诊断技能继续硬编码 `REVIEWED_METRIC`。

## 修正动作

- `apps/api/src/ai-diagnosis/worker.ts` 仅在保存输入确认为 `LIVE_DATA_SCREEN` / `LIVE_SCREEN_INTERNAL_API` / `REALTIME_API` 时复用 `DecisionRun.inputJson`。
- `packages/diagnosis-skills/src/index.ts` 将审计语义改为“正式诊断证据层”：人工复核快照或已校验直播概览实时 API 二选一。
- 新增回归：无 `DataSnapshot` 时，直播概览实时 API 脉冲可创建 `REALTIME_API` 诊断运行，并由 Worker 成功处理。

## 可复用方法

新增证据层、状态层或认证层时，必须同步检查创建入口、后台 Worker、规则引擎、AI 审计、证据目录、前端口径和回归测试。不能只以一个门禁通过作为端到端完成证据。
