# Decision Log

## 2026-07-30 真实数据必须先证明字段归属，再进入正式诊断

- 决策：采集成功定义为“字段名、后台显示值、单位、统计周期和卡片/行列位置具有可审核绑定证据”，不是页面上出现一个可解析数字。`0`、整数和 `0.00` 均是合法值；缺失、`--` 与零严格区分。
- 决策：正式诊断采用当前快照全局失败关闭。任一字段绑定无效、任一表格结构未确认、或历史表格缺少绑定证据时，整个输入降为保守诊断；不得只移除异常字段后继续生成正式动作。
- 决策：表格结构使用“表头 + 当前行唯一业务对象 + 单元格”绑定。首次未知结构必须逐格核对完整张表，不能通过单独确认表头直接放行；完成后才记录同路线、同页面指纹和同表签名的结构校准。只有后续稳定结构通过全部门禁时才允许批量确认原值，结构变化和异常一律重新核对。
- 决策：后台显示值和规范化值以十进制文本贯穿采集、入库与复核；ROI 交叉校验使用精确整数比例，只有正式规则执行可通过共享的受限边界转换为 `number`。超出边界的值视为不可用于规则，而不是静默舍入。
- 原因：相邻“4 万消耗”和“ROI 4”在视觉上都合理，却可能属于不同字段。将数值合理性当证据会把错误业务语义送入诊断；全局门禁和结构指纹能在不扩大采集范围的前提下失败关闭。

### 补充：重复字段与周期值的失败关闭边界

- 决策：服务端收到同一快照内多个候选映射到同一个标准字段时，统一写入 `FIELD_BINDING_AMBIGUOUS`，不得按来源优先级、置信度或相邻位置选取一个值。历史已确认指标若没有 v034 绑定证据，也不属于可信数据。
- 决策：结构签名记录统计周期所在组件位置，不记录“今日/昨日/具体日期”等会自然滚动的周期值；统计周期仍逐次保存并参与字段身份、周期一致性和 ROI 交叉校验。
- 原因：重复候选与无证据历史值都无法证明业务归属；但把周期显示值纳入页面结构指纹会使每日同结构页面反复退化为未知结构，既增加人工负担，也不提高真实性。

## 2026-07-28 采集协议、历史修复与总览口径

### 协议不一致必须失败关闭，可信快照派生状态必须原子写入

- 决策：采集协议作为 shared 契约，由 `/version`、`/extension/context`、Extension 和快照 API 共同校验；任一端缺失或版本不一致时停止上传，不接受兼容猜测。
- 决策：可信 Extension 快照、标准指标、待复核记录、路线状态、心跳和采集批次状态必须在同一事务内成功；读取接口不得补写派生状态。
- 原因：版本错位和部分写入正是“五份快照存在但大屏停在首条”的根因。失败关闭和原子写入让快照存在即有可审计的成熟度状态。

### 历史修复只能补派生记录，不能改变原始证据可信度

- 决策：维护修复工具默认 dry-run，只处理 `VERIFIED` 且派生记录缺失的当前快照；重复执行不得产生新记录，只有实际修复写审计。
- 决策：`MANUAL_PENDING`、冲突、未知或旧路线证据绝不自动升级，原始快照和采集值绝不改写，必须由用户重新采集或人工确认。
- 原因：修复历史不完整性不能等同于重新证明证据可信；否则维护脚本会绕过正常采集与人工校准门禁。

### 总览选择单一来源，路线新鲜度与失败状态分开表达

- 决策：任务总览优先使用本地推总览，缺失时才回退直播概览；同名指标不跨路线求和，每项始终携带来源路线和采集时间。
- 决策：有历史快照但过期的路线显示 `STALE`，路线待确认为 `MANUAL_PENDING`，明确连续失败或活动运行卡住且从未产生快照时才显示 `FAILED`；运行卡住仍会阻断强动作。
- 原因：不同页面的同名 ROI、消耗和订单并不天然同口径，跨路线相加会制造虚假事实；把过期数据涂成失败红色又会掩盖“采到但需刷新”的真实恢复路径。

## 2026-07-28 页面账号 ID 不再进入采集与决策链路

- 决策：移除页面账号 ID 的读取、上传、展示、账号档案录入和采集阻断；页面 URL 参数与可见文本均不得成为账号归属证据。账号隔离改为仅依赖服务端的登录用户、账号档案、项目、任务和可撤销 Extension 凭证归属。
- 决策：数据库旧页面账号列暂不做破坏性迁移。新快照与手工指标固定写入兼容状态 `MATCHED`，表示服务端任务绑定已验证；历史页面账号数据在原始证据 30 天留存任务中到期清除。
- 原因：页面 ID 容易缺失、变化或与用户当前目标页面不一致，不应阻塞用户已通过任务凭证授权的手动采集。服务端任务范围可继续阻止插件跨账号档案访问，同时避免收集不必要的页面身份信息。

## 2026-07-26 识别冲突不得回退为自动确认，待复核状态必须随快照建立

- 决策：路线的 URL、选中分栏或可见标题给出互相冲突的结论时，统一产出 `UNKNOWN`；服务端不得用 URL 或页面类型推断替代冲突的 Popup 路线证据。用户只能从当前任务允许路线中做本次明确选择，且仍受 Extension 凭证、账号任务归属和可信来源校验。
- 决策：已验证快照的标准指标在快照入库事务中立即建立 `PENDING` `ReviewedMetric`，不由大屏读取接口补写；表格单元格仍按实际编辑需要创建独立复核记录。
- 原因：冲突证据若被自动择优会把错误页面归属伪装成可信路线；读取接口带写入副作用则会让数据成熟度取决于用户是否打开某个页面。两项约束使采集事实、人工校准和正式诊断具有稳定可审计的顺序。

## 2026-07-25 标准指标与表格校准共享快照并发语义

- 决策：标准指标的单项、批量和全部确认与表格单元格校准共用当前路线快照、账号/路线确认及 `expectedSnapshotUpdatedAt` 乐观并发门禁；任何校准写入成功都推进对应快照版本。
- 决策：全部确认必须明确提交当前全部可复核快照的版本清单，不能由服务端在写入时静默选择或补齐遗漏路线。
- 原因：正式决策虽然会过滤旧快照，但校准写入若不受当前证据和版本约束，仍可能留下不符合当前事实的审计记录或造成用户误解。统一写入语义可防止旧页面覆盖新采集或其他校准者的最新结论。

### Popup 的一次路线确认必须由服务端上下文证明

- 决策：将 Extension Popup 的“手选路线并点击采集”作为一次完整路线确认，仅在请求具备 `COLLECT` 范围的 Extension 凭证、凭证绑定账号拥有该任务、来源属于两个精确 HTTPS 平台域名、路线配置存在且证据无冲突时写入 `VERIFIED`。非 Extension 入口仍走后续人工路线确认。
- 原因：用户不应为同一笔 Popup 操作确认两次，但不能仅相信客户端的 `manuallyConfirmed` 布尔值；认证类型、任务归属和来源域名必须由服务端独立校验。

### 页面正文只可瞬时用于提取，不能成为快照证据

- 决策：插件可在用户点击确认后的当前浏览器内存中读取少量可见文本，以识别路线、账号和白名单指标；`rawDomText` 不得通过采集快照上传、保存、回传给 AI 或作为正式决策输入。
- 决策：共享快照清洗器强制将 `rawDomText` 置空，API 无条件将数据库字段写为 `null`，不信任插件或其他客户端的声明；保留的证据仅限经过敏感字段清洗的指标、真实结构化表格、来源路线、采集时间和校准审计。
- 原因：单靠插件实现仍可能被其他客户端或未来调用链绕过。共享契约与服务端持久化双重收口既保留诊断所需的最小结构化事实，又避免整页后台内容进入系统。

### 域名授权、路线识别与上传确认保持分层

- 决策：Extension 生产权限只覆盖已核验的 `eos.douyin.com` 与 `localads.chengzijianzhan.cn` 精确域名，不使用泛子域或逐项目 URL 授权；全局路线模板负责页面类型识别，新任务只继承模板。
- 决策：自动识别只读取 URL、标题、选中标签和少量可见标题，不保存或上传页面原文。识别结果不等于采集授权，只有 Popup 中一次明确点击才能读取可见指标/表格并上传；冲突时的下拉选择只对本次采集生效。
- 原因：域名级授权避免每个直播项目重复配置，而路线模板和显式点击共同限制实际采集范围。这样既支持用户主动打开任意目标页，也不会把整个域名下所有页面自动采集。

### 校准记录独立于原始快照，正式决策只读取校准证据

- 决策：标准指标继续使用 `ReviewedMetric`；结构化表格新增按任务、快照、表、行、列唯一定位的 `TableCellReview`。确认、修改和忽略都写独立记录与审计，不覆盖 `DataSnapshot` 原始值。
- 决策：表格批量写入必须验证任务归属、当前路线最新快照、账号与路线确认、`expectedSnapshotUpdatedAt` 并发版本和敏感字段；单批最多覆盖当前分页的 240 个单元格。
- 决策：正式决策只读取当前路线 `CONFIRMED` 或 `MODIFIED` 的指标与表格单元格。`PENDING`、`IGNORED`、过期、缺失、账号/路线未确认和旧快照证据不得参与判断；决策指纹包含表格校准状态和值。
- 原因：采集事实与人工校准需要同时可追溯。独立记录可以保留审计和历史证据，并发令牌防止旧页面覆盖新采集；统一门禁则避免未复核数据通过旧回退路径进入正式动作。

### 审计记录保留最小操作者快照而非级联删除

- 决策：`AuditLog` 使用可空 `userId` 与最小 `{ userId }` 操作者快照。删除用户时数据库外键设为 `ON DELETE SET NULL`；审计动作、范围和操作者快照继续留存。
- 决策：快照仅回填升级前已有的用户 ID，不保存邮箱、姓名或额外个人信息；所有新标准审计写入都使用同一最小快照。
- 原因：审计的不可抵赖性和最小化数据处理必须同时成立。依赖级联删除会抹掉安全和业务追溯证据，而保存更多 PII 没有必要。

### 采集健康采用共享确定性评估器，结构数据由服务端生成

- 决策：采集运行、任务摘要、决策门禁和系统健康统一调用共享诊断评估器；状态、问题码、阻断级别和人工恢复建议不允许由各模块自行推导。
- 决策：5 分钟进入老化、10 分钟过期、连续失败 3 次降级；卡死仅适用于活动运行中的必需路线。`PARTIAL` 是证据质量告警，不是全局正式决策硬阻断。
- 决策：扩展只上报可见页面白名单数据、来源元数据和稳定失败码；版本化结构数据必须由服务端从安全清洗后的原始可见表格生成。
- 决策：历史快照不回填，决策引擎优先读取有效标准任务行，缺少结构数据时回退到旧通用表格解析，避免一次性破坏兼容。
- 决策：小时趋势和素材只先定义契约，取得真实脱敏样本并完成页面校准前不得启用采集器；不得以完整性为由引入自动点击、自动滚动、自动翻页或网络响应拦截。
- 原因：这套边界让采集质量可解释、可测试且来源可追溯，同时把并发、错误诊断和标准化放在可信服务端，不扩大浏览器权限或平台操作能力。

### 第三方提示词只进入可追溯解释参考层

- 决策：`agency-agents` 的相关角色提示词按固定 revision 人工整理为结构化 `decisionReference`，只由 `packages/llm` 和解释接口使用；正式动作继续只来自 `decision-engine`。参考项必须携带来源、真实证据、待补证据、人工步骤、观察指标、停止条件和安全边界。
- 决策：不复制未公开算法排序、通用 ROI/GPM/完播率阈值、自动扩量/降量/暂停或效果承诺；第三方方法不得出现在官方规则引用中，也不得触发审批、预算、状态或平台操作。
- 原因：第三方角色库适合补充审计视角和复核清单，但其通用经验混合了不同平台、行业与自动化假设。固定来源并在解释层隔离，可保留方法价值，同时避免提示词漂移或经验阈值绕过确定性规则与人工审批。

### 暂时隐藏公开注册入口，保留验证能力

- 决策：登录页暂时只提供管理员已发放账号的邮箱密码登录，不展示创建账号、注册后提示或重发验证邮件入口；`/auth/register`、邮箱验证接口和验证页保持原样。
- 原因：当前运营方式由管理员发放账号，先收敛普通用户可见入口；保留验证能力和数据模型可避免恢复开放注册时产生迁移、兼容或安全流程倒退。
- 边界：这是前端可见性调整，不构成服务端邀请制强制控制。真正邀请制必须在服务端对注册资格进行可审计校验，并另行完成设计与测试。

### GET 接口只返回视图状态，不承担生命周期副作用

- 决策：复核指标初始化和建议过期持久化不得由 GET 触发；读取时仅根据 `expiresAt` 派生展示状态，实际状态变更必须在显式写入事务中完成。
- 原因：读取请求可能被轮询、预取、缓存验证或外部观察触发。将初始化、审计或状态迁移放入 GET 会使同一请求既不可预测又难以重试和审计。

### 安全观测与留存作为独立维护职责

- 决策：安全指标仅按 UTC 小时聚合事件类别、次数和数值，不存请求体、身份或凭证；维护任务由独立 Compose 服务执行，不耦合 API 业务进程。
- 原因：安全观测必须避免成为新的敏感数据存储点；留存批处理会占用数据库资源，应与对外请求和优雅停机边界隔离。

### Extension 构建必须按产物而非运行时分离环境能力

- 决策：localhost/loopback 白名单、默认本地 API 地址和本地提示仅由本地构建注入；正式构建字节产物不保留这些字符串或分支。
- 决策：本地测试图标使用独立受控资产；unpacked 与最终 ZIP 使用同一套精确权限、泛域名和禁用标识校验，发布脚本必须在压缩后重新解压验收。
- 原因：仅依赖运行时 `isLocalBuild` 会让生产制品残留本地桥接代码和测试痕迹，不满足最终制品审计要求。

### 账号匹配证据来源使用共享白名单契约

- 决策：账号 ID 证据只接受已登记 URL 参数或人工确认，账号名称证据只接受可见标签或人工确认；类型和 Zod 校验共用同一领域模块。
- 原因：自由字符串无法证明来源语义，也会扩大持久化输入边界。固定来源既保留当前采集兼容性，也阻止插件或外部请求伪造未登记证据类别。

### 开放注册采用验证前暂存，验证后原子建号

- 决策：开放注册仅创建 `PendingRegistration` 与哈希邮箱验证令牌；确认成功后在 Serializable 事务中消费令牌、创建用户和默认工作区、撤销同注册的其余令牌并创建会话。验证令牌为 32 字节随机值，30 分钟过期、单次使用。
- 决策：登录不为待验证注册创建会话；SMTP 仅在生产环境强制 TLS 配置，测试环境只使用内存投递记录。既有用户通过 `emailVerifiedAt` 加法式默认值保持可登录，不虚构历史验证行为。
- 原因：将未验证凭证与可访问账户分离，避免邮箱所有权未确认时获得工作台权限；事务式确认可以防止并发点击同一链接重复建号或留下半完成账户。

### 版本化确认与优雅停机属于可信写入边界

- 决策：批量快照账号确认必须逐项携带 `expectedUpdatedAt`，并在 Serializable 事务中重新校验归属、当前巡检、当前路线与版本；版本变化统一返回冲突而非覆盖新证据。
- 决策：API 终止时先进入 draining、拒绝新业务请求并主动关闭 SSE，再在有限连接排空期后关闭 HTTP 与 Prisma；Compose 对迁移/API/Web 施加最小能力、PID、CPU 和内存约束。
- 原因：页面确认与快照上传可并发发生，未带版本的批量请求会将旧人工判断误写到新证据；优雅停机和资源限制则避免部署切换截断长连接或让单实例资源耗尽。

### 保持模块化单体，按业务边界拆分并设置增长门禁

- 决策：继续使用现有 pnpm Monorepo 和模块化单体，不拆微服务；API 路由、数据库查询、决策表分析、共享契约和页面数据加载分别放入独立模块。
- 决策：关键入口文件设置行数预算并在 CI 执行 `architecture:check`；业务包不得反向依赖 `apps`，新增功能应进入领域模块而不是继续堆入 `server.ts`、共享总入口、规则总入口或任务页。
- 决策：当前快照必须由数据库按任务、最新巡检批次和路线分别取最新记录，禁止先全局截断再在内存分组；可串行化事务统一识别 `P2034` 并有限重试。
- 原因：当前主要维护成本不是业务复杂度本身，而是入口文件职责混杂、查询语义隐含和契约只靠人工约定。模块接缝与自动门禁能缩短定位时间，并防止后续修改重新退化。

### 经营建议必须由当前真实证据触发，不生成填充建议

- 决策：`OptimizationRecommendation` 可以携带可选 `evidence`，商品与投流建议必须引用当前任务已采集表格中的具体商品、投流单元和指标；缺列、样本不足、零分母或异常比例时只报告证据不足，不生成角色排名或扩流候选。
- 决策：删除“至少生成三条建议”及自然/商业流量对照兜底。进房到成交漏斗只有在当前窗口至少存在两个真实环节时才生成，缺失环节保留为缺失。
- 决策：目标 ROI 只使用采集并复核后的 `target_roi`，不提供默认值；它只作为扩流守门线和停止条件，不承诺结果，也不触发自动平台操作。
- 原因：为了数量补齐的通用模板会掩盖数据缺失并制造虚假确定性；将建议绑定到可追溯证据，才能让人工审批、执行和复盘使用同一事实口径。

### 代直播首版只做直播增长，平台权益作为转化资源

- 决策：`SERVICE_PROVIDER_LIVE` 使用 `MANAGED_LIVE_GROWTH`，不进入服务商利润核算；诊断只覆盖流量、直播承接、商品成交、平台活动权益、履约合规和数据可信度。其他操盘模式保持兼容，后续版本再分别细化。
- 决策：平台代金券、补贴、投放券和消返券在代直播模式中属于成交助推资源，不叫平台收益，也不作为服务商成本抵扣展示。只有后台已核验且适用条件明确的权益才能进入到手价、商品和口播建议。
- 原因：代直播的当前交付目标是把直播数据和销售做得更好，混入服务商合同利润会稀释诊断重点；但平台真实权益会直接改善商品吸引力与转化，不能简单删除，必须以核验和合规披露为前提使用。

### 经营优化方案与待审批动作必须分层

- 决策：`DecisionEngineOutput.businessAnalysis` 保存问题、证据、P0/P1/P2 人工优化方案、验证指标、规则边界和官方核验入口；`ActionProposal` 只保存需要进入审批、人工执行和复盘闭环的正式动作。
- 原因：动作去重、冷却、证据不足或安全护栏可能让某轮正式动作数为 0，但这不代表没有可执行的直播、商品或投流优化建议。两层分开既能给出业务价值，也不会让解释性建议绕过审批边界。

### 平台公开规则与经营方法必须明确区分

- 决策：产品只把抖音生活服务官方规则中心和开放平台规则作为合规核验入口；官方经营知识可作为优化方法参考，但不得被表述为强制规则或未公开算法结论。
- 原因：平台规则持续更新，行业阈值和经验玩法也会变化。把第三方经验或历史课程冒充“最新规则”会直接导致错误决策和合规风险。

### Session Cookie 安全属性按环境显式配置，生产默认安全

- 决策：Session Cookie 的 `Secure` 属性由 `SESSION_COOKIE_SECURE` 显式覆盖；未配置时生产环境默认为 `true`、非生产环境默认为 `false`。本地生产镜像通过 HTTP 验收时允许显式设置为 `false`，正式 HTTPS 环境必须保持 `true`。
- 原因：仅依据容器内 `NODE_ENV=production` 会让本地 HTTP 浏览器拒绝保存 Secure Cookie，表现为账号创建时突然登录失效；显式环境配置既保证本地可验收，也不降低正式环境默认安全性。

### 采集任务删除采用事务级联并保留项目级审计

- 决策：错误或重复采集任务允许永久删除；服务端必须校验工作区归属和当前任务确认 ID，在同一事务中删除任务及其级联数据，并创建不引用已删除任务外键的 `COLLECTION_TASK_DELETED` 项目级审计。
- 原因：仅在前端隐藏会留下错误快照和诊断污染；删除后若审计仍绑定任务外键又会被置空而难以追踪，因此删除摘要必须保留原任务 ID、名称和数据数量。

### Extension 使用版本化请求响应桥接，不再用单一页面标记判断在线

- 决策：Web Bridge、Popup 与 Service Worker 共享协议版本和构建指纹；任务页使用带请求 ID 和 5 秒超时的状态请求检测真实后台状态。
- 原因：本地 unpacked 扩展可能出现 Popup 文件已更新但旧 Service Worker 仍运行的半更新状态。单一 DOM 标记只能证明桥接脚本存在，不能证明后台可响应或协议兼容。

### 同一直播大屏按用户当前分栏分别采集

- 决策：概览、商品、流量作为三条独立采集路线；用户手动切换平台分栏后主动采集，插件通过 URL、真实选中状态和专属字段识别当前分栏，无法识别时只允许本次人工确认。
- 原因：页面导航会同时包含多个分栏文字，使用普通文本匹配会误判；自动切换平台标签又会突破只读采集安全边界。独立路线保留证据来源，也能避免同一分栏重复上传覆盖其他分栏。

### Web 一键配对只传递一次性任务码和脱敏状态

- 决策：任务页可经允许来源的 Web Bridge 把一次性六位任务配对码交给插件；Bridge 只返回连接状态，不返回 Token、Cookie、凭证或采集原文。
- 原因：普通用户不应理解 API Token 和任务 ID，同时网页与插件之间必须保持最小信息面和账号隔离。

### 账号档案是业务归属根，项目不再承担账号身份

- 决策：采用 `AccountProfile -> Project -> CollectionTask -> CollectionRouteSource` 层级；平台账号 ID 为优先唯一标识。
- 原因：项目代表活动或经营阶段，一个账号会重复使用多个项目；把账号身份放在项目名称中会导致历史复用困难和跨账号串档。

### 账号不确定的数据必须隔离，不能靠名称猜测归属

- 决策：快照分为 `MATCHED / MISMATCHED / UNVERIFIED`。不一致直接拒绝，无法识别只保存待确认证据，不生成正式指标。
- 原因：同名账号、账号改名和页面字段缺失都可能导致错误合并；宁可进入人工校准，也不能污染其他账号诊断。

### 项目复用只复制配置，不复制历史事实

- 决策：同账号内可复用主体、操盘、合作关系、服务商和成本配置创建新项目；不复制任务、快照、指标、诊断、动作、审批、执行或复盘。
- 原因：配置可以复用，历史事实必须保持原项目归属，才能保证审计、对比和结果复盘可信。

### 错误账号档案采用显式确认的事务级永久删除

- 决策：账号卡片提供删除入口；确认框必须说明会删除全部项目、任务和诊断闭环数据。服务端按账号归属在单一事务中级联删除，并在工作区保留删除摘要审计。
- 原因：重复迁移或误建档案可能已经包含项目和任务，仅隐藏档案无法真正清理错误数据；显式不可恢复提示、所有权校验、名称确认和事务审计共同降低误删风险。

本文件记录影响项目方向、架构边界和安全边界的重要决策。

## 已确认决策

### 保留主体识别优先，不回退泛化投流系统

- 决策：系统继续优先识别投流主体和服务商场景，不回退成泛化投流诊断工具。
- 原因：第一阶段聚焦巨量本地推 / 本地生活 / 服务商，主体差异会影响指标解释、诊断路径和动作建议。

### 第一版只做诊断、建议、审批、复盘，不自动执行

- 决策：第一版闭环只覆盖诊断、动作建议、人工审批、人工执行记录和复盘。
- 原因：投放平台动作属于高风险操作，必须保留人工确认和人工执行边界。

### ReviewedMetric 是人工复核层，不替代 DataSnapshot / NormalizedMetric

- 决策：`ReviewedMetric` 作为人工复核层存在，不替代原始快照 `DataSnapshot` 和标准化指标 `NormalizedMetric`。
- 原因：需要同时保留原始证据、标准化结果和人工复核结果，便于审计和回溯。

### MetricKey 是标准指标口径入口

- 决策：`MetricKey` 是标准指标口径入口，`normalize` / `review-metrics` / `decision-engine` 均使用标准 key。
- 原因：统一口径可降低不同页面字段名、别名和来源差异导致的误判。

### packages/llm 降级为解释层，不生成最终动作

- 决策：`packages/llm` 只做解释层，不生成最终动作。
- 原因：最终动作需要可控、可测试、可审计的结构化规则，由确定性决策引擎承担。

### decision-engine 负责最终结构化动作建议

- 决策：`decision-engine` 负责最终结构化动作建议。
- 原因：动作建议需要稳定输入、明确阈值、人工检查项和审批护栏。

### ActionOutcome 只记录人工执行后的复盘，不触发平台动作

- 决策：`ActionOutcome` 只记录人工执行后的复盘结果，不触发任何平台动作。
- 原因：复盘是闭环记录，不应越过安全边界变成自动执行能力。

### 部署先走服务器 staging，不立即切正式域名

- 决策：部署先走服务器 staging，不立即切正式域名。
- 原因：当前需要先验证腾讯云 Ubuntu Docker 环境、网络、数据库、构建和运行稳定性；未备案时不建议把 `www.pxxis.cn` 指向广州服务器。

### 未确认主体或未复核数据不能产生强动作

- 决策：主体待校准、主体字段冲突、未复核数据、低置信关键指标和模糊 ROI 均阻断预算调整与暂停类动作。
- 原因：完整字段不等于可信证据；任何强动作必须建立在已确认主体和足够复核覆盖率上。

### 客户端脱敏不能替代服务端安全边界

- 决策：Extension 保存/上传前脱敏，API 在校验后、入库前再次使用共享脱敏器处理全部快照表面。
- 原因：API 可能被非官方客户端直接调用，服务端必须独立保证认证信息和个人信息不落库。

### 关键写入使用事务和幂等键

- 决策：快照、DecisionRun、ActionOutcome 使用作用域唯一幂等键，业务写入与 AuditLog 处于同一事务。
- 原因：网络重试、并发提交或审计失败不得产生重复业务记录或审计缺口。

### 旧分析接口只保留解释兼容

- 决策：`/explain` 为解释入口，旧 `/analyze` 仅兼容并返回弃用头，不再创建 `Recommendation` 或最终动作。
- 原因：诊断和动作必须只有 `decision-engine` 一个口径，避免 Web/API 出现双轨结论。

### Staging 默认不暴露数据服务

- 决策：PostgreSQL 仅加入 Compose 内网；Web/API 端口仅绑定宿主机 `127.0.0.1`，由反向代理对外服务。
- 原因：数据库和应用进程不应直接暴露公网，生产入口统一交给 HTTPS 反向代理。

### Web 会话使用 HttpOnly Cookie，Extension 保留 Bearer token

- 决策：Web 浏览器通过 `HttpOnly + SameSite=Lax` Cookie 维持一小时会话，不在浏览器 Storage 保存 JWT；Extension 使用独立 Bearer 认证链路。V0.2.3 起其凭证由一次性账号配对产生，不再由用户手工配置通用 Token。
- 原因：降低 Web XSS 读取 JWT 的风险，同时让插件上传拥有独立、可撤销且账号隔离的认证边界。

### Extension 最终发布物必须进入自动测试

- 决策：构建同步 unpacked 发布目录，release 命令生成唯一版本 ZIP，测试直接解压 ZIP 检查安全边界。
- 原因：源码安全不代表旧发布包安全，最终交付物必须和源码接受同一套护栏。

### 旧诊断和策略表以 ignored legacy model 过渡

- 决策：删除旧 Recommendation API/DTO 和未启用 StrategyRule 运行时代码，数据库旧表暂以 `@@ignore` 保留。
- 原因：先消除双口径和客户端认知负担，同时避免未经 migration 直接删除历史数据。

### 固定页面巡检必须由用户主动启动

- 决策：Extension 只在用户主动开启巡检后，读取用户已经打开的白名单页面；不得自动导航、创建标签、点击或提交页面操作。
- 原因：需要提高数据覆盖率，同时继续遵守只采集、不代替用户操作平台的永久安全边界。

### 采集批次和路线质量是强动作前置证据

- 决策：使用 `CollectionRun` 聚合一次巡检的多路线快照，默认 5 分钟内为新鲜、10 分钟后过期；必需路线缺失、数据过期或路线连续失败时阻断强动作。
- 原因：单个页面快照无法证明数据覆盖完整，也不能保证建议使用的是同一时间窗口的数据。

### 动作建议必须具备服务端生命周期治理

- 决策：建议由服务端执行有效期、同类去重/替代、冷却和频率限制；客户端展示状态但不负责关键判断。
- 原因：避免重复、陈旧或高频建议造成操作压力，并保证状态变更可审计、可并发控制。

### 决策预演不得产生业务写入

- 决策：预演复用确定性规则和数据质量判断，但不创建决策记录、动作建议或审计记录。
- 原因：用户需要先查看规则输出和阻断原因，预演本身不应改变业务状态。

### AI 解释熔断不影响确定性决策

- 决策：AI 解释连续失败达到阈值后短时熔断，健康中心明确展示降级；确定性决策引擎继续工作。
- 原因：LLM 仅是解释层，外部服务异常不能中断核心诊断和安全规则。

### 最新巡检批次优先且建议治理按项目串行化

- 决策：只要任务存在 `CollectionRun`，决策必须以最新批次为锚点；建议去重、过期和频控检查在 PostgreSQL 项目级事务锁内完成。
- 原因：旧快照不得绕过新批次的缺页阻断，并发决策也不得在检查与写入之间产生重复建议或突破频控。

### 生产 Extension 不再拦截平台网络响应

- 决策：公开生产构建删除 injected 脚本及 fetch/XHR 补丁，只保留可见 DOM、真实表格、截图/OCR、CSV 和人工校准。
- 原因：网络响应正文并非诊断必需证据，其兼容性和账号风险不值得生产环境承担。

### 实时信号与正式建议采用双速链路

- 决策：MetricPulse 进入单实例有界内存并通过 SSE 生成事实信号；正式 ActionProposal 仍由持久化快照和 decision-engine 生成。
- 原因：操盘手需要低延迟态势提示，但实时噪声不能绕过确定性规则、审批和人工执行边界。

### 未知字段按动作证据依赖降级

- 决策：保留主体和来源可信度的全局安全阻断，其他未知字段只阻断依赖该证据的动作；人工别名确认后恢复资格。
- 原因：避免平台字段漂移造成全局降级，同时禁止系统自动猜测 ROI 口径。

### 建议并发使用任务级批次门禁和数据库 Gate/Quota

- 决策：删除项目级阻塞锁，使用项目+任务的非阻塞事务批次门禁、动作 Gate 和固定小时 Quota。
- 原因：一次决策的建议必须原子成批，同时不同任务可以并发，避免项目级锁造成连接池等待。

### 根 package.json 是唯一产品版本源

- 决策：Workspace、Extension manifest、API、Web、Side Panel 和发布 ZIP 从根版本派生，并写入 Git SHA、构建时间和 SHA256。
- 原因：代码、数据库和制品必须可追溯，版本不一致或脏工作树不得发布。

### Extension 使用账号级一次性配对凭证

- 决策：Web 为指定 `AccountProfile` 生成五分钟一次性配对码；插件兑换为三十天可撤销的最小权限凭证，服务端仅保存 SHA-256 哈希。
- 原因：普通用户不应理解或手工复制 API Token、任务 ID；凭证必须天然绑定账号并禁止审批、执行和跨账号访问。

### 不完整采集只允许保守预演

- 决策：正式 DecisionRun 在服务端再次校验账号、主体、指标复核和基础采集路线；任一关键门槛不满足时返回 `DECISION_NOT_READY`，仅保留无业务写入的预演。
- 原因：单页或单份 CSV 不能代表直播大屏、本地推总览和任务列表的完整证据，不能据此创建预算或暂停类正式建议。

### 手工指标是受控兜底而非绕过采集安全

- 决策：手工/CSV 导入必须确认账号，经过服务端脱敏、标准化、复核和审计；敏感认证字段拒绝，未知列进入漂移队列。
- 原因：平台页面变化时需要可用兜底，但人工入口不能绕过账号隔离、数据可信度和敏感信息边界。

### 插件连接与采集必须以任务为可见上下文

- 决策：配对码可携带 `collectionTaskId`，插件兑换后自动绑定该任务；心跳持续显示当前账号、项目、任务和页面状态。
- 原因：只绑账号但不显示任务会让操盘手不确定数据将上传到哪里，也无法在 Web 中判断插件是否可用。

### 任务页按数据成熟度渐进展示

- 决策：无快照时不显示诊断、动作、漂移和原始证据；首次上传后显示合并数据大屏，复核后才展示诊断操作。
- 原因：普通用户必须先完成当前唯一任务，后置技术信息不应在尚无数据时增加认知负担。

### 多页采集按本轮每路线最新证据合并

- 决策：采集汇总、人工复核和决策输入统一使用最新 `CollectionRun` 中每条路线的最新快照。
- 原因：单张最新快照会丢失其他页面证据，同一路线全量快照又会引入重复和旧值。

### 整体支付 ROI 与全域支付 ROI 是不同口径

- 决策：`pay_roi` 表示整体支付 ROI，`full_domain_pay_roi` 表示全域支付 ROI，页面适配器不使用模糊“支付 ROI”子串将两者合并。
- 原因：两个口径用于不同的即时转化与全域溢出判断，误合并会直接污染决策证据。

### 采集完整度与正式决策资格分层

- 决策：`PARTIAL` 表示页面已经采集但只覆盖当前可见区域；只要必需路线存在、账号逐条确认且指标完成复核，就允许创建正式 DecisionRun。单项缺失由 `actionEligibility` 阻断依赖动作，不再把所有 `blockingReasons` 升级为全局阻断。
- 原因：直播大屏天然包含 Canvas、虚拟列表和分栏，只用 `COMPLETE` 作为正式诊断门槛会让真实页面永久无法继续；同时预算、暂停和 ROI 调整仍必须满足各自证据要求。

### 服务商支付 ROI 不等于服务商后毛利 ROI

- 决策：服务商算法继续以核销毛利除以广告消耗、服务费和商家补贴后的真实成本计算盈利；页面采集到的支付/核销 ROI 只能作为账号表现事实，缺少真实毛利时不得生成依赖盈利判断的强动作。
- 原因：支付 ROI 很高并不代表计入服务费和商家成本后仍盈利，二者混用会产生错误放量结论。

### DecisionRun 成为唯一的新诊断主线

- 决策：新诊断统一写入 `AI_SKILL_ORCHESTRATED` DecisionRun；`AiAnalysisTask` 和 `LEGACY_RULE` 只为历史兼容，不再生成新 mock 诊断。
- 原因：消除“规则正式诊断 + mock 专家参考”双轨，明确区分模型诊断、确定性安全裁决和人工执行。

### 业务诊断以版本化 Skills 编排

- 决策：确定性代码负责数据门禁、证据选择和指标计算；DeepSeek 通过 Tool Calls 调用版本化领域 Skills，再生成受 Schema 和证据 ID 约束的综合诊断。
- 原因：让诊断方法可测试、可归因、可离线升级，同时禁止模型自由发挥或隐藏推理进入业务记录。

### AI 候选动作必须经过规则护栏

- 决策：AI 只能提出枚举内、引用合法证据的候选动作；数据质量、动作证据、风险、冷却、去重、频控、有效期和审批资格均由服务端确定性代码裁决。
- 原因：AI 负责提出和解释假设，但不能决定预算、状态、权限或平台执行。

### 案例只离线学习，不在线自改

- 决策：成功诊断与 Outcome 形成 DRAFT 案例，满足质量条件后再由人工纳入；首期使用工作区内结构化 SQL/内存加权排序，不使用 embedding。案例和 Outcome 不在线修改 Prompt、规则或 Skill。
- 原因：保证租户隔离、可审计和版本归因，避免单个错误 Outcome 直接污染线上策略。

### DeepSeek 编排采用确定性首审与两阶段综合

- 决策：`audit_data_readiness` 由编排器作为第一个 Skill 确定性执行；DeepSeek Tool Calls 负责领域 Skill 选择。领域输出后先用 thinking 生成带合法证据 ID 的短核心裁决，再用无 thinking 的 JSON 综合器展开完整诊断。空参数 Skill 使用 Zod 验证对象类型并忽略不读取的额外字段。
- 原因：DeepSeek thinking 模式实际拒绝 named/required `tool_choice`；把 audit 作为唯一可用工具仍不能由接口强制。完整诊断若让每个领域和最终 JSON 重复 thinking，会超过 120 秒。两阶段设计保留核心 AI 推理、结构修复和证据校验，同时在正式串行 24 例中达到 100%/100%/0/0。

### 领域模型输出允许窄结构规范化但不放宽业务契约

- 决策：Zod 校验前只允许把 0–1 数字字符串转换为 number、把明确的单值集合包装为数组，并在有事实/假设时把无拒答原因的 `refused=null` 归一为 false；枚举、证据 ID、事实内容和动作含义不做纠正。
- 原因：这些差异是供应商 JSON 表示波动，不涉及业务推断。窄规范化能减少无价值的格式重试；规范化后仍必须通过原 Schema、证据目录和规则护栏。

### 未登记历史库必须先对账演练，验收任务不得跨库替代

- 决策：对没有 Prisma 迁移历史的既有数据库，禁止直接执行 `prisma migrate deploy`。先对原库执行可恢复备份、Schema/行数清单和校验，从备份克隆演练库；仅在演练库以当前 Prisma Schema 生成差异、审查并事务执行一次性对账脚本，且确认空差异、迁移状态、历史读取和行数一致后，才可对原库再次备份并执行同一脚本与迁移登记。
- 决策：一次性对账脚本必须锁定显式目标库和验收任务，且在应用前验证数据库名、历史基线、无其他客户端、行数清单、Schema/差异摘要。验收任务不存在时必须停止；不得通过复制任务、切换目标库或弱化门禁完成升级。
- 原因：迁移目录描述的是目标状态，不能证明未知历史库可安全直接迁移。将演练与原库执行绑定到同一清单和任务，可避免跨库混用“已升级”和“可真实验收”的结论。
